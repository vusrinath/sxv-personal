what is OAuth2 ?
================================================================================

ANSWER: What is OAuth 2.0
================================================================================

OAuth 2.0 is an AUTHORIZATION framework (not authentication) that allows a
third-party application to access a user's resources on another service WITHOUT
exposing the user's password.

Think of it like a valet key for your car — it lets someone drive your car but
they can't open the trunk or glove box. OAuth 2 gives limited access without
sharing your full credentials.

--------------------------------------------------------------------------------
THE PROBLEM IT SOLVES
--------------------------------------------------------------------------------

Without OAuth:
  1. App X wants to access your Google contacts
  2. App X asks for your Google username + password
  3. You give it — now App X has FULL access to your Google account
  4. Dangerous: App X could read your email, delete files, etc.

With OAuth 2:
  1. App X redirects you to Google's login page
  2. YOU log in directly with Google (App X never sees your password)
  3. Google asks: "App X wants to read your contacts. Allow?"
  4. You click Allow
  5. Google gives App X a TOKEN with LIMITED access (contacts only)
  6. App X uses that token — can read contacts but NOTHING else

--------------------------------------------------------------------------------
KEY CONCEPTS
--------------------------------------------------------------------------------

ROLES:
  - Resource Owner    = You (the user who owns the data)
  - Client            = The app requesting access (e.g., a mobile app)
  - Authorization Server = The server that issues tokens (e.g., Google Auth)
  - Resource Server   = The server hosting your data (e.g., Google Contacts API)

TOKENS:
  - Access Token      = Short-lived token the client uses to call APIs
                        (typically 15 min to 1 hour)
  - Refresh Token     = Long-lived token used to get a new Access Token
                        when the old one expires (without re-login)

SCOPES:
  - Define WHAT the client can access
  - Examples: "read:contacts", "write:calendar", "profile:email"
  - User sees these during consent: "This app wants to: Read your contacts"

--------------------------------------------------------------------------------
OAUTH 2.0 GRANT TYPES (FLOWS)
--------------------------------------------------------------------------------

1. AUTHORIZATION CODE GRANT (most common, most secure)
   - For server-side web apps
   - Flow:
     Client → redirects user to Auth Server
     User → logs in, grants consent
     Auth Server → redirects back with an Authorization Code
     Client (server-side) → exchanges Code for Access Token (server-to-server)
   - Why secure: Token exchange happens server-to-server, never exposed to browser

2. AUTHORIZATION CODE + PKCE (Proof Key for Code Exchange)
   - For mobile apps and Single Page Apps (SPAs)
   - Same as above but adds a code_verifier/code_challenge to prevent interception
   - RECOMMENDED for all public clients (apps that can't store a secret)

3. CLIENT CREDENTIALS GRANT
   - For machine-to-machine (no user involved)
   - The client authenticates with its own credentials (client_id + client_secret)
   - Example: A backend service calling another backend service

4. IMPLICIT GRANT (DEPRECATED - don't use)
   - Was for SPAs, returned token directly in URL fragment
   - Insecure: token exposed in browser history/logs
   - Replaced by Authorization Code + PKCE

5. RESOURCE OWNER PASSWORD GRANT (DEPRECATED - don't use)
   - Client collects username/password directly
   - Defeats the purpose of OAuth; only for legacy/migration scenarios

--------------------------------------------------------------------------------
HOW THE MOST COMMON FLOW WORKS (Authorization Code)
--------------------------------------------------------------------------------

  +--------+                               +---------------+
  |        |---(1) Authorization Request-->|   Auth Server  |
  |        |                               | (e.g., Google) |
  |  User  |<--(2) Login Page-------------|               |
  |        |---(3) Credentials + Consent-->|               |
  +--------+                               +-------+-------+
                                                    |
                                           (4) Auth Code
                                                    |
                                                    v
  +--------+                               +-------+-------+
  |        |<--(4) Redirect with Code------|               |
  | Client |                               |   Auth Server  |
  |  App   |---(5) Code + Client Secret--->|               |
  |        |<--(6) Access Token + Refresh--|               |
  +--------+                               +---------------+
       |
       |---(7) API call with Access Token-->  Resource Server
       |<--(8) Protected Resource ----------  (e.g., Contacts API)

Step by step:
  1. Client redirects user to: https://auth.google.com/authorize?
       client_id=abc&redirect_uri=https://myapp.com/callback&scope=contacts&response_type=code
  2. User logs in at Google
  3. User consents to the requested scopes
  4. Google redirects back: https://myapp.com/callback?code=xyz123
  5. Client's SERVER sends code + client_secret to Google's token endpoint
  6. Google returns: { "access_token": "...", "refresh_token": "...", "expires_in": 3600 }
  7. Client calls API: GET /contacts  Authorization: Bearer <access_token>
  8. Resource server validates token and returns data

--------------------------------------------------------------------------------
OAUTH 2 vs AUTHENTICATION
--------------------------------------------------------------------------------

  OAuth 2.0 = AUTHORIZATION (what can you access?)
  OpenID Connect (OIDC) = AUTHENTICATION (who are you?)

  OIDC is a layer ON TOP of OAuth 2 that adds:
  - An ID Token (JWT containing user identity info)
  - A /userinfo endpoint
  - Standard scopes: openid, profile, email

  When people say "Login with Google" they usually mean OIDC (built on OAuth 2).

--------------------------------------------------------------------------------
ACCESS TOKEN FORMATS
--------------------------------------------------------------------------------

Two common formats:

1. OPAQUE TOKEN (random string)
   - Example: "ya29.a0AfH6SMBx..."
   - Resource server must call Auth Server to validate it
   - Used by Google, GitHub, etc.

2. JWT (JSON Web Token) — self-contained
   - Example: "eyJhbGciOiJSUzI1NiIs..."
   - Contains claims (user_id, scopes, expiry) signed by Auth Server
   - Resource server can validate locally (just verify the signature)
   - Used by Auth0, Okta, Azure AD, etc.

--------------------------------------------------------------------------------
COMMON OAUTH 2 PROVIDERS
--------------------------------------------------------------------------------

  - Google (accounts.google.com)
  - Microsoft / Azure AD (login.microsoftonline.com)
  - GitHub (github.com/login/oauth)
  - Okta (your-org.okta.com)
  - Auth0 (your-tenant.auth0.com)
  - AWS Cognito
  - Keycloak (open-source, self-hosted)

--------------------------------------------------------------------------------
REAL-WORLD ANALOGY
--------------------------------------------------------------------------------

  Hotel Key Card analogy:
  - You (Resource Owner) check in at the front desk (Authorization Server)
  - Front desk gives you a key card (Access Token)
  - Key card opens YOUR room and the gym (Scopes) but NOT other rooms
  - Key card expires at checkout (Token Expiry)
  - If you lose it, front desk can deactivate it (Token Revocation)
  - You don't give your ID to the gym — you just swipe the card

--------------------------------------------------------------------------------
SECURITY BEST PRACTICES
--------------------------------------------------------------------------------

  - Always use HTTPS
  - Use Authorization Code + PKCE (never Implicit)
  - Store tokens securely (server-side session, NOT localStorage)
  - Keep access tokens short-lived (15 min)
  - Validate redirect_uri strictly (prevent open redirect attacks)
  - Use state parameter to prevent CSRF
  - Validate token scopes on the resource server
  - Implement token revocation for logout

--------------------------------------------------------------------------------
SUMMARY
--------------------------------------------------------------------------------

  OAuth 2.0 = A framework that lets apps access your stuff without your password
  
  Key pieces:
    - Authorization Code flow (for web apps)
    - PKCE (for mobile/SPA)
    - Client Credentials (for machine-to-machine)
    - Access Tokens (short-lived, limited access)
    - Refresh Tokens (long-lived, get new access tokens)
    - Scopes (define what access is granted)
  
  Add OIDC on top if you also need to know WHO the user is (authentication).
